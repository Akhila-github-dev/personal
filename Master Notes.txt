   * Difference between synchronized and concurrent hashmap 
Ans) Collections.synchronizedMap() → makes the whole map thread-safe using a single lock
ConcurrentHashMap → designed for concurrency using fine-grained locking / lock-free techniques
✅ 1. Collections.synchronizedMap()
📌 Usage:
Map<Integer, String> map =
    Collections.synchronizedMap(new HashMap<>());
⚙️ How it works:
Entire map is locked for every operation
Only one thread at a time can access it
🔁 Return Type:
Map<K, V>
⚠️ Iteration requires manual synchronization:
synchronized (map) {
    for (Integer key : map.keySet()) {
        System.out.println(key);
    }
}
✅ 2. ConcurrentHashMap
📌 Usage:
ConcurrentHashMap<Integer, String> map =
    new ConcurrentHashMap<>();
⚙️ How it works:
Uses segment-level locking (Java 7) or bucket-level CAS (Java 8+)
Multiple threads can read/write simultaneously
🔁 Return Type:
ConcurrentHashMap<K, V>
✅ No need for manual synchronization during iteration:
for (Integer key : map.keySet()) {
    System.out.println(key);
}
📊 Comparison Table
| Feature          | synchronizedMap                         | ConcurrentHashMap           |
| ---------------- | --------------------------------------- | --------------------------- |
| Locking          | Single lock (whole map)                 | Fine-grained / bucket-level |
| Performance      | Slower under high concurrency           | Faster                      |
| Thread Safety    | Yes                                     | Yes                         |
| Iteration        | Must manually sync                      | No need                     |
| Null keys/values | Allows 1 null key, multiple null values | ❌ Not allowed               |
| Scalability      | Poor                                    | High                        |

Q: Which thread pool is used by parallelStream()?
By default, parallelStream() uses the ForkJoinPool.commonPool(), a shared thread pool that uses a work-stealing algorithm to efficiently execute tasks in parallel.

Can we use our own ForkJoinPool?
Yes. If you don't want to use the common pool, you can submit the parallel stream to a custom ForkJoinPool:

ForkJoinPool pool = new ForkJoinPool(4);

This limits the parallelism to 4 worker threads instead of using the common pool.

   * In-depth questions about HashMap (internal working, hashcode calculation, value overriding, collision, time complexity) [02:43]
HashMap stores data as key-value pairs. Internally, it uses an array of buckets, where each bucket stores one or more Node objects.

When we call put(key, value), HashMap first calls hashCode() on the key to generate a hash value. It then applies an internal hashing function and calculates the bucket index.
In Java, this is effectively done using (n - 1) & hash, where n is the table size. The default initial capacity is 16.

If the bucket is empty, a new node is inserted. If another key maps to the same bucket, a collision occurs. HashMap then compares the keys using equals().
If the keys are equal, the existing value is replaced. Otherwise, a new node is added to the bucket.

Before Java 8, collisions were handled using a linked list. From Java 8 onwards, if a bucket contains more than 8 entries and the table size is at least 64,
the linked list is converted into a red-black tree to improve lookup performance from O(n) to O(log n).

Ans)
| Feature                             | Local Variables                                                    | Instance Variables                                                                 |
| ----------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| **Where declared**                  | Inside a method, constructor, or block                             | Inside a class but outside methods                                                 |
| **Scope**                           | Only within the method/block where declared                        | Accessible to all instance methods of the object                                   |
| **Lifetime**                        | Created when method starts, destroyed when method ends             | Exists as long as the object exists                                                |
| **Memory location**                 | Stored in **stack memory**                                         | Stored in **heap memory** as part of the object                                    |
| **Default value**                   | ❌ No default value – must be initialized before use                | ✅ Gets default values (0, null, false, etc.)                                       |
| **Access modifiers**                | ❌ Not allowed (no public/private)                                  | ✅ Allowed (public, private, protected, default)                                    |
| **Synchronization / Thread safety** | Usually **thread-safe** because each thread has its own stack copy | **Not thread-safe by default** because multiple threads may access the same object |

Synchronization in Java
Local variables:
They do not need synchronization because each thread works with its own copy.

Instance variables:
They are shared between threads, so they may require synchronization (using synchronized, locks, etc.) if multiple threads modify them.

6. Method References
A method reference is a shorthand form of a lambda expression.
Example
Lambda:
list.forEach(x -> System.out.println(x));
Method reference:
list.forEach(System.out::println);

Types:
Reference to static method
Reference to instance method
Reference to constructor
1. Reference to a Static Method

Syntax:

ClassName::staticMethodName

Example:

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<Integer> list = Arrays.asList(3, 1, 2);

        // Lambda
        list.sort((a, b) -> Integer.compare(a, b));

        // Method reference
        list.sort(Integer::compare);

        System.out.println(list);
    }
}

Explanation:
Refers to a static method of a class.
Integer::compare replaces (a, b) -> Integer.compare(a, b).

2. Reference to an Instance Method of a Particular Object

Syntax:
instance::instanceMethodName

Example:

import java.util.function.Consumer;

public class Main {
    public static void main(String[] args) {
        Main obj = new Main();

        // Lambda
        Consumer<String> c = s -> obj.print(s);

        // Method reference
        Consumer<String> c2 = obj::print;

        c2.accept("Hello");
    }

    void print(String msg) {
        System.out.println(msg);
    }
}

Explanation:
Refers to an instance method of a specific object.
obj::print replaces s -> obj.print(s).

3. Reference to an Instance Method of an Arbitrary Object of a Particular Type

Syntax:
ClassName::instanceMethodName

Example:

import java.util.*;

public class Main {
    public static void main(String[] args) {
        List<String> list = Arrays.asList("a", "c", "b");

        // Lambda
        list.sort((a, b) -> a.compareTo(b));

        // Method reference
        list.sort(String::compareTo);

        System.out.println(list);
    }
}

Explanation:
Refers to an instance method, but the object is not specified.
The object is provided later (by the JVM).
String::compareTo replaces (a, b) -> a.compareTo(b).

4. Reference to a Constructor
Syntax:
ClassName::new

Example:

import java.util.function.Supplier;

public class Main {
    public static void main(String[] args) {
        // Lambda
        Supplier<String> s1 = () -> new String();

        // Method reference
        Supplier<String> s2 = String::new;

        System.out.println(s2.get());
    }
}

Explanation:
Refers to a constructor.
Useful for object creation in functional programming.

| Type                        | Syntax                | Example             |
| --------------------------- | --------------------- | ------------------- |
| Static method               | `Class::staticMethod` | `Integer::compare`  |
| Instance (specific object)  | `obj::method`         | `obj::print`        |
| Instance (arbitrary object) | `Class::method`       | `String::compareTo` |

2️⃣ LinkedList Explanation

A LinkedList is a linear data structure where elements are stored as nodes.
Each node contains:
Data
Reference (pointer) to the next node
Reference to the previous node (in doubly linked list)

Structure:

[Prev | Data | Next] <-> [Prev | Data | Next] <-> [Prev | Data | Next]

Example:
10 -> 20 -> 30 -> 40

Here:

10 points to 20
20 points to 30
30 points to 40

3️⃣ Types of LinkedList (Concept)

1️⃣ Singly Linked List

10 -> 20 -> 30 -> 40 -> null

Each node points only to the next node.

2️⃣ Doubly Linked List (Used in Java LinkedList)

null <- 10 <-> 20 <-> 30 <-> 40 -> null

Each node has:
previous pointer
next pointer

3️⃣ Circular Linked List

10 -> 20 -> 30 -> 40
 ^               |
 |_______________|

Last node points back to the first node.

4️⃣ LinkedList Example in Java
import java.util.LinkedList;

public class Example {

[10, 20, 30]
5️⃣ When to Use LinkedList

Use LinkedList when:

Many insertions/deletions
Data size changes frequently
You don't need fast random access
Use ArrayList when:
You need fast access by index
Mostly reading data

Question 1: Explain JVM Memory Model
Interview Answer

JVM (Java Virtual Machine) is responsible for running Java applications. It manages memory and executes Java bytecode.

The JVM memory is divided into:

1. Heap Memory

Stores objects and instance variables.
Shared among all threads.
Garbage Collector removes unused objects.

2. Stack Memory

Stores local variables and method calls.
Each thread has its own stack.
Thread-safe because stacks are not shared.

3. Metaspace

Stores class metadata, method information, and runtime constant pool.
Introduced in Java 8 (replaced PermGen).

4. Program Counter (PC Register)

Stores the address of the current JVM instruction being executed.
Each thread has its own PC Register.

5. Native Method Stack

Used when Java calls native methods written in languages like C or C++.
Why are local variables thread-safe?

Every thread has its own stack, so local variables are not shared.

Heap objects are shared between threads, so multiple threads can modify the same object, leading to race conditions unless synchronization is used.

Earlier, Java provided Thread and Runnable for concurrency. Nowadays, we usually use ExecutorService, which manages a thread pool and reuses threads instead of
creating a new thread for every task. We submit Runnable or Callable tasks to it. Runnable doesn't return a result, while Callable can return a value and throw 
checked exceptions. When a Callable is submitted, it returns a Future, which can be used to retrieve the result using get(), although get() blocks until the task 
completes. Java 8 introduced CompletableFuture, which allows asynchronous programming without blocking. It supports chaining operations with methods like thenApply(),
thenAccept(), and thenCompose(), making it ideal for calling multiple independent services in parallel, such as in microservices.

| ExecutorService            | CompletableFuture                                                         |
| -------------------------- | ------------------------------------------------------------------------- |
| Manages thread pools       | Builds asynchronous workflows                                             |
| Executes Runnable/Callable | Executes async tasks and chains operations                                |
| Uses Future                | Uses CompletableFuture                                                    |
| `Future.get()` blocks      | `thenApply()`, `thenAccept()`, `thenCompose()` are non-blocking callbacks |
| Good for background tasks  | Good for async APIs and microservices                                     |

15. How many ways to create thread pools in Java
 The Executors utility class provides several factory methods.

1. Fixed Thread Pool ⭐ (Most Common)
ExecutorService executor =
        Executors.newFixedThreadPool(5);
Creates a fixed number of threads.
Reuses the same threads.

Example:

5 threads

Task1 → Thread1
Task2 → Thread2
Task3 → Thread3
Task4 → Thread4
Task5 → Thread5
Task6 → waits until a thread becomes free

Used when you know approximately how many tasks should run concurrently.

2. Cached Thread Pool
ExecutorService executor =
        Executors.newCachedThreadPool();
Creates threads as needed.
Reuses idle threads.
Can create many threads if the workload grows.

Best for many short-lived asynchronous tasks.

3. Single Thread Executor
ExecutorService executor =
        Executors.newSingleThreadExecutor();

Only one thread processes all tasks.

Task1
 ↓
Task2
 ↓
Task3

Used when tasks must execute in order.

4. Scheduled Thread Pool
ScheduledExecutorService executor =
        Executors.newScheduledThreadPool(2);

Used for delayed or periodic execution.

Example:

executor.schedule(() -> {
    System.out.println("Runs after 5 seconds");
}, 5, TimeUnit.SECONDS);

Or every 10 seconds:

executor.scheduleAtFixedRate(task, 0, 10, TimeUnit.SECONDS);
5. Work Stealing Pool (Java 8)
ExecutorService executor =
        Executors.newWorkStealingPool();
Uses multiple processors efficiently.
Idle threads can "steal" work from busy threads.
Useful for CPU-intensive tasks.
Summary
Thread Pool	Purpose
newFixedThreadPool()	Fixed number of reusable threads (most common)
newCachedThreadPool()	Creates threads as needed for many short tasks
newSingleThreadExecutor()	Executes tasks one by one in sequence
newScheduledThreadPool()	Runs tasks after a delay or periodically
newWorkStealingPool()	Optimizes CPU-intensive parallel work
Interview Answer

Java provides several ways to create thread pools using the Executors class. The most commonly used are newFixedThreadPool() for a fixed number of reusable threads,
newCachedThreadPool() for dynamically creating threads, newSingleThreadExecutor() for sequential task execution, newScheduledThreadPool() for delayed or periodic
tasks, and newWorkStealingPool() for efficient parallel execution of CPU-intensive tasks.

16. D/f b/w hashmap and concurrent hashmap.

Feature                	HashMap                        	ConcurrentHashMap
Thread Safety            	❌ No	                        ✅ Yes (bucket-level locking)
Performance	                ✅ Fast (Single-threaded)	    ✅ Fast (Multi-threaded)
Null Keys	                   ✅ Allowed                  	❌ Not Allowed
Null Values                	✅ Allowed	                    ❌ Not Allowed
Synchronization	            ❌ None                        	✅ Uses locks per segment

1. HashMap
✅ Non-thread-safe → It does not provide any synchronization, making it unsafe for multi-threaded environments.
✅ Allows null keys & values → Supports one null key and multiple null values. 
✅ Fast Performance → Since it has no locks, it performs better in single-threaded environments.

2. ConcurrentHashMap
✅ Thread-safe → Uses locks at the bucket level, allowing multiple threads to modify different parts of the map simultaneously. 
✅ Better performance than synchronizedMap → Reduces contention in multi-threaded environments. 
✅ Does NOT allow null keys or values → Prevents null-related errors in concurrent applications.

Use HashMap in single-threaded applications where performance is critical.

Use ConcurrentHashMap in multi-threaded environments to ensure safe concurrent access.

   * In-depth questions about HashMap (internal working, hashcode calculation, value overriding, collision, time complexity) [02:43]
HashMap stores data as key-value pairs. Internally, it uses an array of buckets, where each bucket stores one or more Node objects.

When we call put(key, value), HashMap first calls hashCode() on the key to generate a hash value. It then applies an internal hashing function and calculates the bucket index.
In Java, this is effectively done using (n - 1) & hash, where n is the table size. The default initial capacity is 16.

If the bucket is empty, a new node is inserted. If another key maps to the same bucket, a collision occurs. HashMap then compares the keys using equals().
If the keys are equal, the existing value is replaced. Otherwise, a new node is added to the bucket.

Before Java 8, collisions were handled using a linked list. From Java 8 onwards, if a bucket contains more than 8 entries and the table size is at least 64,
the linked list is converted into a red-black tree to improve lookup performance from O(n) to O(log n).

2. Why is insertion at the beginning O(n)?

Suppose:
[A, B, C, D]
If you insert X at index 0, it becomes:

[X, A, B, C, D]
Every existing element has to shift one position to the right, so the work grows with the number of elements: O(n).

Adding at the end is usually O(1) because you simply place the new element in the next available slot. Only when the internal array is full does
resizing make that single insertion more expensive.

"What is N+1 problem in Hibernate?"
"N+1 is a performance problem that can occur when Hibernate fetches a list of parent entities using one query and then executes an additional query for each parent
entity to load its associated child entities.
For example, if I have 100 departments and I fetch all departments using one query, and then access employees for each department inside a loop,
Hibernate may execute one query for departments and 100 additional queries for employees. So instead of 1 query, we end up with 101 queries.

This is called the N+1 problem. We can avoid it using techniques such as JPQL JOIN FETCH, EntityGraph, or batch fetching depending on the use case."
"Why does it happen?"
It commonly happens when an association is lazy-loaded and we access that association for multiple parent entities, especially inside a loop. Hibernate then
triggers a separate SQL query for each parent."

| `@Primary`                            | `@Qualifier`                           |
| ------------------------------------- | -------------------------------------- |
| Gives one bean **default preference** | Explicitly selects a **specific bean** |
| Used when multiple beans exist        | Used when multiple beans exist         |
| Less specific                         | More specific                          |
| Can be used at class level            | Usually used at injection point        |

➡️ SmsService is injected.

“@Primary defines the default bean when multiple beans of the same type are available, whereas @Qualifier is used to explicitly specify
which bean should be injected. @Qualifier has higher priority than @Primary.”

Authentication is the process of verifying the user's identity. In our Spring Boot application, when the user logs in, the request is intercepted by Spring Security's filter chain.

If the nested operation fails and the situation is handled appropriately, Spring can roll back to the savepoint without necessarily rolling back 
everything in the outer transaction.

Think:

REQUIRED → same transaction

REQUIRES_NEW → completely new transaction

NESTED → same transaction + savepoint

Interview questions you should prepare

Q1. What is Propagation.REQUIRED?

One important caveat: NESTED behavior depends on the transaction manager/database support for savepoints, and @Transactional behavior
also depends on how the method is invoked (Spring proxy/self-invocation matters).


=====================================================================
@Transactional
public void placeOrder() {
    saveOrder();

    paymentService.processPayment();  // REQUIRES_NEW

    updateOrder(); // Something goes wrong here
}
// PaymentService
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void processPayment() {
    makePayment();
}

Both methods are in different classes, so the Spring proxy works normally.

What happens?

When placeOrder() starts:

Transaction A starts
      ↓
saveOrder()
      ↓
processPayment()
      ↓
Transaction A is suspended
      ↓
Transaction B starts (REQUIRES_NEW)
      ↓
makePayment()
      ↓
Transaction B COMMIT
      ↓
Transaction A resumes
      ↓
updateOrder()
      ↓
ERROR ❌
      ↓
Transaction A ROLLBACK
Final result

Payment → COMMITTED ✅
Order changes → ROLLED BACK ❌

Because processPayment() has REQUIRES_NEW, its transaction is independent of the transaction of placeOrder().

So if the interviewer asks:

“After processPayment() succeeds, something fails in placeOrder(). Will payment also roll back?”

Answer:

“No. Since processPayment() uses REQUIRES_NEW, it runs in a separate transaction. Its transaction commits independently. 
If placeOrder() fails afterward, only the outer transaction rolls back; the payment transaction remains committed.”

3. Centralized Token Validation & Refresh Handling
Instead of adding JWT validation in every controller, interceptors handle it globally.

When a client sends an HTTP request, it first reaches the DispatcherServlet, which acts as the front controller in Spring Boot.

The DispatcherServlet consults the HandlerMapping to identify the appropriate controller method based on the URL and HTTP method.

Once the correct handler is found, the request is passed to the HandlerAdapter, which invokes the corresponding controller method (like one annotated with @GetMapping or @PostMapping).

Inside the controller, the request is processed and typically delegated to the service layer, where the business logic resides.

To secure REST APIs in Spring Boot, I use Spring Security along with JWT-based authentication.

First, the user sends credentials (username/password) to an authentication endpoint. If the credentials are valid, the server generates a JWT token, which contains user details and roles in the payload.

This token is then sent by the client in every request using the Authorization header (Bearer token).

On the server side, I implement a JWT filter that intercepts each request, extracts the token, validates its signature and expiry, and sets the authentication in the Spring Security context.

Based on the roles present in the token, I apply role-based authorization using configurations like hasRole() or hasAuthority().

Since JWT is stateless, we don’t store session data on the server, which improves scalability.

Service Registry vs. Service Discovery in Microservices
In a microservices architecture, managing how services find and communicate with each other is crucial. This is where Service Registry and Service Discovery come into play.
1. Service Registry
The Service Registry is like a phone directory where all microservices register themselves and can be dynamically located by other services.
How it Works:
When a microservice starts, it registers its location (IP, port) in the registry.
The registry stores and maintains this information.
Other microservices query the registry to find and communicate with registered services.
Examples of Service Registry Tools:
Eureka (Netflix) – Used in Spring Cloud ecosystems.
Consul (HashiCorp) – Supports service discovery and health checks.
Zookeeper (Apache) – Helps coordinate distributed systems.
2. Service Discovery
Service Discovery enables microservices to find and connect with other services dynamically without hardcoding IP addresses.
Types of Service Discovery:
Client-Side Discovery
The client asks the Service Registry for a service instance.
Example: Netflix Eureka in Spring Cloud.
Server-Side Discovery
A Load Balancer (like Nginx or Kubernetes Service) sits in front of services.
The balancer queries the registry and routes requests dynamically.

Closed: Requests flow normally. If failures exceed a threshold, it moves to Open.
Open: Requests are blocked immediately to prevent further strain on the failing service.
Half-Open: After a timeout, a few test requests are allowed. If they succeed, the circuit closes again.
In Spring Boot, we typically implement this using Resilience4j. For example, we annotate a method with @CircuitBreaker and provide a fallback method to 
handle failures gracefully. This helps maintain user experience even when a downstream service is down.

An API Gateway is a single entry point for all client requests to a microservices system.
It acts as a reverse proxy, routing requests to the correct microservice, handling cross-cutting concerns like:

🧠 Why Do We Need It?
Microservices often depend on each other.
If Service A calls Service B and B is down, A keeps retrying → leads to thread exhaustion, slowness, or system crash.
Circuit breaker solves this by failing fast.

⚡ Example Scenario
Call State	  Behavior
Service B       healthy	Calls from Service A work as normal
Service B       fails	Circuit breaker tracks failures
Threshold           reached	Circuit opens, calls are blocked temporarily
Wait                 period ends	Circuit tests a request (half-open state)
Recovery	              If successful, circuit closes again

🏗 Circuit Breaker States
State	      Meaning
Closed	    Normal operation; all requests pass through.
Open	       Service is considered down; calls are blocked.
Half-Open	    Allows limited requests to test recovery.

In our microservices system, we used Resilience4j for circuit breaking. If a downstream service (like Inventory) failed beyond
a threshold, the circuit opened and requests were short-circuited for 10 seconds to prevent overloading. We provided fallback responses 
for a better user experience and allowed limited trial calls in a half-open state to check recovery.

💡 Difference Between Circuit Breaker and Retry
Feature    	Circuit Breaker	    Retry
Fail fast	            ✅ Yes	  ❌ No
Protect system      	✅ Yes	  ❌ No
Repeat calls	        ❌ Blocks calls	✅ Retries N times

| Propagation     | Simple meaning                                                                    |
| --------------- | --------------------------------------------------------------------------------- |
| `REQUIRED`      | Join existing transaction; if none exists, create a new one                       |
| `REQUIRES_NEW`  | Always create a **new transaction**; suspend existing transaction                 |
| `SUPPORTS`      | Use existing transaction if available; otherwise execute without transaction      |
| `NOT_SUPPORTED` | Always execute **without transaction**; suspend existing transaction              |
| `MANDATORY`     | Must have an existing transaction; otherwise exception                            |
| `NEVER`         | Must NOT have an existing transaction; otherwise exception                        |
| `NESTED`        | Execute inside a **nested transaction/savepoint** within the existing transaction |


@Transactional(propagation = Propagation.REQUIRED)
public void placeOrder() {
    processPayment();
}
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void processPayment() {
}

Assume placeOrder() starts Transaction A.

When it calls processPayment():

placeOrder()
   ↓
Transaction A
   ↓
processPayment()
   ↓
Transaction B (new)

Transaction A is suspended while B executes.

If processPayment() succeeds → B commits.

Then control returns to placeOrder() → A continues.

3. Scenario: Payment fails

Suppose:

@Transactional
public void placeOrder() {
    saveOrder();
    processPayment();   // REQUIRES_NEW
    updateOrder();
}

If processPayment() throws a runtime exception:

Transaction B → ROLLBACK
Transaction A → can also rollback if exception propagates

So REQUIRES_NEW does NOT automatically mean the outer transaction won't roll back.

The important point is:

The inner transaction rolls back independently, but if its exception propagates to the outer method, the outer transaction can also roll back.

4. What if processPayment() succeeds but placeOrder() fails?

This is the classic interview question.

Transaction A → placeOrder
      ↓
Transaction B → processPayment → COMMIT
      ↓
Transaction A → FAIL → ROLLBACK

Payment transaction B remains committed.

The order transaction A rolls back.

So you can end up with:

Payment successful, but order rolled back.

That's one reason REQUIRES_NEW must be used carefully.

5. What if you remove REQUIRES_NEW?

Then it becomes REQUIRED by default:

@Transactional
public void placeOrder() {
    saveOrder();
    processPayment();
}

@Transactional   // REQUIRED by default
public void processPayment() {
}

Now both use the same transaction:

Transaction A
 ├── placeOrder
 └── processPayment

If processPayment() fails and the exception causes the transaction to roll back:

placeOrder → ROLLBACK
processPayment → ROLLBACK

Everything is rolled back together.

6. NESTED scenario
@Transactional
public void placeOrder() {
    saveOrder();
    processPayment(); // NESTED
    updateOrder();
}

Conceptually:

Transaction A
   |
   |--- saveOrder
   |
   |--- SAVEPOINT
   |       |
   |       └── processPayment
   |
   |--- updateOrder

*What is Caching?
Caching is a technique used to store frequently accessed data in a temporary storage location for faster retrieval. 
Instead of fetching data from a slow source (like a database or API), caching allows systems to reuse previously 
retrieved or computed data, improving performance and reducing load times.

How Caching Works
Cache Hit – If requested data is found in the cache, it is returned instantly.
Cache Miss – If data is not in the cache, it is fetched from the original source and stored in the cache for future use.
Eviction Policy – When the cache reaches its storage limit, older or less frequently used data is removed based on policies 
like LRU (Least Recently Used) or LFU (Least Frequently Used).

Factory Pattern: Creates objects without specifying the exact class to create.
 Example: A notification system where you decide at runtime whether to send an Email, SMS, or Push Notification.

Suppose you have different notification types:
Email
SMS
Push

Your application decides at runtime which notification object it needs.

Without Factory:
if (type.equals("EMAIL")) {
    EmailNotification email = new EmailNotification();
}
else if (type.equals("SMS")) {
    SMSNotification sms = new SMSNotification();
}
The client has to know about all the concrete classes.

Factory removes that responsibility.

Step 1 — Create interface
public interface Notification {
    void send();
}
Step 2 — Implement it
public class EmailNotification implements Notification {

    @Override
    public void send() {
        System.out.println("Sending Email");
    }
}
public class SMSNotification implements Notification {

    @Override
    public void send() {
        System.out.println("Sending SMS");
    }
}
Step 3 — Create Factory
public class NotificationFactory {

    public static Notification createNotification(String type) {

        if (type.equalsIgnoreCase("EMAIL")) {
            return new EmailNotification();
        }

        if (type.equalsIgnoreCase("SMS")) {
            return new SMSNotification();
        }

        throw new IllegalArgumentException("Invalid type");
    }
}

Now the client simply does:

Notification notification =
        NotificationFactory.createNotification("EMAIL");

notification.send();

Output:
Sending Email

The client doesn't need to know:
new EmailNotification()
new SMSNotification()

The Factory handles object creation.
Factory = "You tell me what you need; I'll create the object for you."
Factory is a creational design pattern that encapsulates object creation and returns an appropriate implementation based on 
some input or condition. It allows the client to create objects without directly depending on their concrete classes.

Abstract Factory Design Pattern

This is where people usually get confused.
Factory
Creates one type of product.

Example:

NotificationFactory

   → Email
   → SMS
   → Push
Abstract Factory

Creates families of related objects.

Imagine you're building a UI.

You have:

Windows UI
    Button
    Checkbox

Mac UI
    Button
    Checkbox

You want the entire UI to belong to the same family.

Interfaces
interface Button {
    void click();
}
interface Checkbox {
    void check();
}
Windows products
class WindowsButton implements Button {

    public void click() {
        System.out.println("Windows Button");
    }
}
class WindowsCheckbox implements Checkbox {

    public void check() {
        System.out.println("Windows Checkbox");
    }
}
Mac products
class MacButton implements Button {

    public void click() {
        System.out.println("Mac Button");
    }
}
class MacCheckbox implements Checkbox {

    public void check() {
        System.out.println("Mac Checkbox");
    }
}
Abstract Factory
interface UIFactory {

    Button createButton();

    Checkbox createCheckbox();
}

Windows factory:

class WindowsFactory implements UIFactory {

    public Button createButton() {
        return new WindowsButton();
    }

    public Checkbox createCheckbox() {
        return new WindowsCheckbox();
    }
}

Mac factory:

class MacFactory implements UIFactory {

    public Button createButton() {
        return new MacButton();
    }

    public Checkbox createCheckbox() {
        return new MacCheckbox();
    }
}

Client:

UIFactory factory = new WindowsFactory();

Button button = factory.createButton();
Checkbox checkbox = factory.createCheckbox();

button.click();
checkbox.check();

The important point is:

             UIFactory
             /       \
            /         \
 WindowsFactory      MacFactory
     /     \           /     \
 Button  Checkbox    Button  Checkbox
Easy way to remember

Factory → creates an object/product

Abstract Factory → creates a family of related objects
Abstract Factory is a creational design pattern that provides an interface for creating families of related objects without specifying their concrete classes.

Builder Design Pattern

Suppose you have a class with many fields:

User user = new User(
    "Akhila",
    27,
    "Hyderabad",
    "abc@gmail.com",
    "9999999999",
    true
);

This becomes difficult to understand.

Which value represents what?

Also, what if some fields are optional?

Builder solves this.

User class
class User {

    private String name;
    private int age;
    private String city;
    private String email;

    private User(Builder builder) {
        this.name = builder.name;
        this.age = builder.age;
        this.city = builder.city;
        this.email = builder.email;
    }

    public static class Builder {

        private String name;
        private int age;
        private String city;
        private String email;

        public Builder name(String name) {
            this.name = name;
            return this;
        }

        public Builder age(int age) {
            this.age = age;
            return this;
        }

        public Builder city(String city) {
            this.city = city;
            return this;
        }

        public Builder email(String email) {
            this.email = email;
            return this;
        }

        public User build() {
            return new User(this);
        }
    }
}

Now creating the object becomes:

User user = new User.Builder()
        .name("Akhila")
        .age(27)
        .city("Hyderabad")
        .email("abc@gmail.com")
        .build();

Much easier to read.

Why is this called Builder?
Because you're building the object step by step.

===== JAVA MULTITHREADING: ADVANCED =====

1. A service uses a volatile counter, but increments are still lost under load. Why, and how would you fix it?

volatile guarantees visibility and ordering for reads and writes of that variable, but it does not make a compound operation such as count++ atomic. Two threads can read the same value and both write back the same incremented value.

For a standalone counter, use AtomicInteger or LongAdder. LongAdder is usually preferable for a highly contended statistics counter, while AtomicInteger is useful when callers need an atomic read-modify-write result. If the counter must remain consistent with other fields, protect the complete invariant with one lock or transaction rather than making only the counter atomic.

AtomicInteger count = new AtomicInteger();
count.incrementAndGet();

2. A production JVM has many BLOCKED threads and requests are timing out. How would you investigate a possible deadlock?

Capture several thread dumps close together using jcmd <pid> Thread.print or jstack <pid>. Look for threads waiting for locks, the lock owners, repeated lock cycles, and whether the JVM reports a deadlock. Correlate thread names with request or executor logs, then inspect the code paths acquiring those locks.

Fix the lock ordering so every path acquires shared locks in the same order, reduce nested locking, or redesign shared mutable state. If a timed lock is appropriate, ReentrantLock.tryLock(timeout, unit) can prevent indefinite waiting; handle timeout and interruption deliberately. A timeout alone does not repair unsafe state transitions.

3. An ExecutorService handles a traffic spike by creating a growing queue, and latency keeps increasing. What is the failure mode and what would you change?

An unbounded queue converts overload into steadily increasing latency and memory use. Bound both the worker count and queue capacity, expose active-thread, queue-depth, rejection, and task-duration metrics, and define what the caller should do when capacity is exhausted. A rejection policy can fail fast or apply backpressure; silently dropping work is only valid when the operation is explicitly disposable.

Keep blocking I/O away from a small CPU-bound pool. Size pools based on measured workload and downstream limits, and ensure shutdown drains or cancels tasks according to the application's delivery guarantees.

4. Two requests concurrently run "if (!map.containsKey(key)) map.put(key, value)". Why is this unsafe with ConcurrentHashMap?

Each map operation is thread-safe, but the pair of operations is not atomic. Both requests can observe that the key is missing and both perform initialization. Use an atomic map operation such as computeIfAbsent:

Value value = map.computeIfAbsent(key, this::loadValue);

Keep the mapping function short and avoid recursively updating the same map from that function. If initialization has external side effects, use a separate idempotency or coordination strategy; a concurrent map cannot make an external operation transactional.

===== SPRING BOOT: ADVANCED SCENARIOS =====

1. A method annotated with @Transactional rolls back when called through another bean, but not when called from another method on the same object. Why?

In the usual proxy-based Spring configuration, transactional behavior is applied when a call crosses the Spring proxy. A call such as this.saveInner() is a self-invocation and bypasses that proxy, so the inner method's transaction attributes are not applied independently.

Move the transactional operation to another Spring bean and call that bean through injection, or restructure the transaction boundary. Also remember that Spring rolls back by default for unchecked exceptions and Error, not checked exceptions; specify rollbackFor when checked exceptions must trigger rollback. Avoid solving this by exposing or injecting the bean's own proxy unless the design requires it.

2. A client retries a slow POST request and creates duplicate orders. How would you make the operation safe under concurrent retries?

Accept an idempotency key scoped to the caller and operation. Persist the key, request identity, and result under a database uniqueness constraint in the same transaction as the order. A repeated request with the same key and same payload returns the recorded result; reusing the key with a different payload is rejected. Handle a concurrent unique-key conflict by reading and returning the already-recorded result.

An application-level "check then insert" is insufficient because concurrent requests can both pass the check. Keep a business-key unique constraint as a final safeguard, and define how long idempotency records must be retained.

3. A Spring Boot endpoint is fast for a few records but becomes slow and memory-heavy when returning thousands of entities. What would you change?

First measure the request across controller, service, database, and serialization, then inspect generated SQL and query plans. Avoid loading an unbounded entity graph. Use pagination or a DTO projection for API responses, fetch only required columns, and address N+1 queries with an appropriate fetch join, EntityGraph, or batch fetching.

Be careful combining collection fetch joins with pagination: joins can multiply rows and make database-level paging incorrect or inefficient. For large exports, use a controlled streaming or batch approach, keep transactions short where possible, and avoid collecting the entire result in memory before writing the response.

4. A singleton @Service stores the current user's ID in an instance field to reuse it across method calls. What can go wrong?

Spring singleton beans are shared by concurrent requests. A request-specific mutable field can be overwritten by another request, causing data leaks or incorrect authorization decisions. Keep request state in method-local variables and pass it explicitly. Use an appropriate request-scoped object only when lifecycle-bound state is genuinely required, and do not treat scope as a replacement for clear ownership of mutable data.

5. @Async work started inside a @Transactional method fails after the original method returns. Does the async task share the transaction?

No. Spring's ordinary imperative transactions are bound to the calling thread; they do not automatically propagate to a separate async thread. The original transaction may commit or roll back independently while the async task runs. Give the async operation its own transaction if it needs one.

If the async task must only run after a successful database commit, use a transactional event listener with AFTER_COMMIT or, for reliable cross-process delivery, a transactional outbox. A plain in-memory async submission can be lost if the process stops after committing the database change.

===== MICROSERVICES: ADVANCED SCENARIOS =====

1. An order transaction commits in one service, but publishing its Kafka event fails. How do you prevent the database and event stream from diverging?

Use the transactional outbox pattern. In one local database transaction, write both the order change and an outbox row describing the event. A separate publisher reads unsent rows and publishes them, marking them delivered only after successful publication. If it crashes after publishing but before marking the row, it may publish again, so consumers must be idempotent.

This avoids pretending that a database transaction and a Kafka publish are one atomic transaction. Monitor the age and volume of pending outbox rows and define retry and cleanup behavior.

2. A Kafka consumer performs a database update, then crashes before committing its offset. What should the application expect, and how do you handle it?

The record can be delivered again. Design the consumer for at-least-once delivery: identify each event with a stable ID and record processed IDs or make the business update idempotent in the same database transaction. Commit the offset only after the durable business operation succeeds, using the consumer framework's appropriate acknowledgment mode.

Kafka transactions can provide exactly-once processing for supported Kafka-to-Kafka workflows, but they do not automatically make an arbitrary external database or HTTP side effect exactly-once. State the guarantee at each system boundary and make retries safe.

3. A downstream service is intermittently slow. Why can retries make the incident worse, and how should resilience be configured?

Retries add traffic precisely when the downstream service may already be overloaded. Use finite timeouts at every network boundary, a small retry budget with exponential backoff and jitter for transient failures, and retry only operations that are safe to repeat. Add a circuit breaker to stop calls when failure rates are high and a bulkhead or bounded concurrency limit to protect local resources.

Use fallbacks only when a truthful degraded response exists; do not return fabricated success. Track timeout rate, retry count, circuit state, saturation, and end-to-end latency. Coordinate timeout and retry budgets across the call chain so nested retries do not multiply unexpectedly.

4. A payment succeeds, but the order service fails before recording the result. How do you preserve consistency across the services?

There is no single local @Transactional boundary that atomically commits both services' databases. Model the workflow as a Saga with explicit states and compensating actions. For example, record the order as pending, request payment with an idempotency key, and transition the order after receiving a durable payment result. If a later step fails, issue an idempotent refund or other compensation and track it until completion.

Use an outbox for reliable event publication, deduplicate messages, make state transitions repeatable, and provide reconciliation for ambiguous timeouts where a payment may have succeeded but its response was lost. Compensation is a business action, not a literal rollback of history.

5. A new service version needs a database schema change while old instances are still running. How do you deploy without downtime?

Use an expand-migrate-contract rollout. First add backward-compatible schema elements, such as a nullable column, while old code continues to work. Deploy code that can read both representations and writes the new representation. Backfill existing data in controlled batches, verify it, then deploy code that relies only on the new representation. Remove the old schema only after all old application versions and rollback paths are gone.

Make migrations observable and restartable, avoid long exclusive locks, and test the old and new application versions against the transition schema. Application rollback must remain possible at each stage.

6. A service has rising Kafka consumer lag even though its instances are healthy. What would you inspect?

Compare incoming production rate with per-consumer processing throughput; inspect lag by partition, rebalance frequency, processing latency, error and retry rates, and time spent waiting on databases or downstream APIs. Check whether the topic has enough partitions for the intended parallelism and whether a hot key is concentrating work in one partition.

Scale consumers only up to the useful partition parallelism, then address the actual bottleneck: optimize processing, batch safe operations, bound downstream calls, or isolate slow work. Do not skip or commit failed records just to reduce the lag metric; define a retry and dead-letter policy that preserves recoverability.

===== ADVANCED TROUBLESHOOTING QUESTIONS =====

1. An API is slow, but application CPU is low. How would you find the bottleneck?

Use a request trace or correlation ID to compare time spent in application code, database calls, external services, queue waits, and serialization. Check connection-pool and thread-pool saturation, DNS and network latency, database slow-query logs, and the query execution plan. Low CPU often points to waiting or contention, not a need for more CPU.

Change one measured bottleneck at a time and compare latency distributions, especially tail latency, before and after the change. Avoid relying only on averages, which can hide a small but important group of very slow requests.

2. A retry, fallback, or cache appears to hide errors, but customers report stale or incorrect results. What is your response?

Treat correctness as a separate requirement from availability. Identify which responses were served from cache or fallback, establish freshness and consistency requirements with the business, and expose that degraded state through logs and metrics where appropriate. Set explicit cache TTL and invalidation behavior; never turn an unknown outcome into a success response.

For writes, use idempotency keys and durable status tracking so a timeout can be resolved by querying the operation's state rather than blindly repeating a side effect. Add tests for partial failures and recovery, not only the successful path.
